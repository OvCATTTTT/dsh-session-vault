# 架构与设计取舍

## 三层结构

```
查询 ──► ① 关键词库（自动挖掘，可 pin/mute）
              │  沿共现边扩散 1~2 级
              ▼
         ② 摘要（带 seq 区间锚点）
              │  按锚点精确跳转
              ▼
         ③ 原文（全量，只增不删）
```

**关键词不是"存储层"，是"索引层"。** 它由摘要文本自动切出（中文 bigram + ASCII 词），
按 `df ≥ termMinDf` 过滤后进入词库。不需要人工维护词表，也不依赖任何外部词库。

## 为什么这样分层

单靠原文相似度检索，两个问题无解：

1. **成本和噪声**：原文 13k 条，每次查询都扫一遍既慢又容易召回一堆不相关的。
2. **不知道自己不知道**：模型不会主动去查，除非有人告诉它"这儿有东西"。

摘要层的作用是**便宜的粗筛 + 可读的索引条目**；`seq_from/seq_to` 让"看摘要"能精确
落到"看原文的那几行"，而不是再做一次相似度匹配。

## 打分公式（调过两轮）

```
score = 查询词覆盖率 + 0.25 × 扩散词覆盖率      （上限 1）
```

**必须只把查询词本身算进主分子。** 早先版本把扩散出来的几十个词一起算进分子分母，
结果任何一条摘要都能凑够一堆词，分数全部饱和到 1，完全失去区分度（实测确实如此）。

覆盖率 = Σ(命中查询词的 idf 权重) / Σ(全部查询词的 idf 权重)。只命中 1 个词时最多
拿 1/N 分，自然被阈值滤掉——这正是"别把只提到'权限'两个字的摘要当成 ACL 报错的答案"。

## 增量与幂等

| 机制 | 实现 |
|---|---|
| 文件增量 | `source_files.bytes_done` 字节水位，只解新帧 |
| 摘要去重 | `summaries.hash` UNIQUE，重复导入直接跳过 |
| 事件去重 | `events.ukey` UNIQUE（session + seq + kind + 序号） |
| spool 幂等 | 行内 `hash` + 字节偏移水位 |
| 联想链实时性 | 边表 **查询时实时读**，入库即生效，**不需要 reindex** |

最后一点是本方案与"文件式记忆库 + 定期重建索引"的核心区别：那边新增记忆和索引更新
之间有延迟窗口，且重建是 O(N)；这边写边是 O(k²)·k≈24，微秒级。

## 边权重为什么用饱和函数

```
w = 1 - e^(-hits / 5)
```

线性累加的问题是高频词（"插件""可以"）会积累几百次共现，然后吞噬所有联想结果。
饱和函数在 hits=5 时就到 0.63、hits=20 到 0.98，收敛且不会失控。

## 中文检索的三个坑（都实测过）

| 做法 | 结果 |
|---|---|
| FTS5 默认 `unicode61` | ❌ 中文整句成一个 token，检索完全失效 |
| FTS5 `trigram` | ⚠️ 要求查询 ≥3 字符，"项目""火锅""方案"全部漏掉 |
| **bigram 预分词 + `unicode61`** | ✅ 2 字查询也命中（本方案采用） |

## 会话日志的三个坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 8.6 MB 文件只解出 195 字节 | `.jsonl.zstd` 是**多帧串联**，`zstdDecompressSync` 只解第一帧 | 扫 magic `28 b5 2f fd`，按偏移逐帧解 |
| 尾部写入中 | 最后一帧未写完，解压必然失败 | 停在它之前，不推进水位，下次再来 |
| 压缩数据里恰好出现 magic | 假阳性切分 | 与后续帧合并重试（最多 4 次） |

## 检索性能（四轮实测优化）

优化前后都在同一份真实语料上测（64 个会话 / 3,996 条摘要 / 189k 共现边）。

| 轮次 | 改动 | 整条 gate | 扩散词数 |
|---|---|---|---|
| 初版 | — | **227 ~ 326 ms** | 4,826 ~ 9,735 |
| ① | 每节点只取 hits 最高的 30 条边 + 每层最多 100 节点 + 总量上限 400 | 43 ~ 69 ms | capped 400 |
| ② | hub 词（`tool-result`/`助手`/`content`，df 占摘要总数绝大部分）不进打分池 | 43 ~ 69 ms（倒排行数 15,200 → 数百） | 400 |
| ③ | `minEdgeHits = 2` 剪掉只共现过一次的弱边（308k → 189k） | — | 400 |
| ④ | **惰性扩散**：先用查询词本身打分，命中已够就不扩散 | **0.3 ~ 3 ms** | 0（大多数查询） |

最坏情况（长中文句触发完整扩散）**43 ms**；空查询、只有常见词、完全没出现过都在
0.1 ms 以内。

关键点是第 ④ 轮：**大多数查询根本不需要联想**。查询词本身是低频词时，直接打分
就能凑够 top-3，扩散只是白白花掉 20~40 ms。把扩散推迟到"第一遍没凑够"之后，
中位耗时直接掉到个位数毫秒。

`spread()` 的三个上限任何一个去掉都会退化：
- 去掉 `maxNeighbors`：hub 词一跳带出几千个词
- 去掉 `maxFrontier`：第二层扇出指数增长
- 去掉 `maxSpreadTerms`：兜底失效，长句会爆到上万词

## 体积构成（实测）

13,440 条事件 / 3,970 条摘要 / 34k 关键词 / 308k 共现边：

| 项 | 体积 |
|---|---|
| 事件原文 | 12.4 MB |
| 摘要正文 | 3.5 MB |
| `terms_inv` | 447,586 行 |
| `term_edges` | 308,039 行 |
| **dsh.db 合计** | **约 83 MB** |

体积主要来自 bigram 全文索引和倒排表。三个旋钮可以压：

- `termMinDf`（默认 2）—— 提高会显著减少关键词与边
- `termMaxCount`（默认 8000）—— 硬上限
- `ftsMaxChars`（默认 20000）—— 每条事件只索引前 N 字符

## 为什么不用向量（v0.1）

三个理由：

1. **bigram + 共现已经覆盖了大部分场景。** 中文的字符重叠度高，换个说法往往还有共享字。
2. **向量会静默地"看起来对但不对"地召回**，比没有更难排查。先有可解释的关键词层，再加向量做兜底，顺序反了会很难定位问题。
3. **引入依赖就引入失败面。** 现在整个插件零运行时依赖，不需要模型、不需要常驻服务、不需要网络。

`summaries` / `events` 表都预留了扩展空间，将来加向量只需新增一列和一个兜底通道，
不影响现有链路。
