# 向量检索提案（未实施）

> 状态：**暂不实施**。2026-11-26 调研后决定先不上。
> 这份文档记的是**查证过的事实**和到时候要避开的坑，不是待办事项。

---

## 一、结论

当前检索（词法匹配 + 共现扩散 + hub 降权）够用，向量检索**投入产出比不划算**：

- 能带来的提升是有限的（主要是压掉"字面像、语义无关"的假阳性）
- 代价是 50 MB 依赖 或 每条消息 300ms+ 网络延迟
- 而这个插件的第一原则是「零运行时依赖、绝不拖垮宿主」

真要做，只能做「向量重排」，不能做「向量召回」——理由见第四节。

---

## 二、查证到的事实

### DSH 宿主没有任何 embedding 能力

```
profile 里的 @deepseek-ai 包：只有 cosmokit、schemastery
unpacked 部分：dsh-session-log-export、libreoffice-kit（与 embedding 无关）
```

**结论**：插件想上向量，embedding 必须自己解决。

### DeepSeek 官方没有 embedding 接口

只提供 chat / completions（V4、R1 系列），没有 `text-embedding` 类端点。
所以"用 DeepSeek 顺便算向量"这条路不存在。

### 数据规模很小（2026-11-26 实测）

| | |
|---|---|
| 摘要 | 485 条 |
| 平均长度 | 779 字 |
| 合计 | 37.8 万字 |
| 事件 | 11,182 条（9.1 MB） |

1536 维 × 485 条 × 4 字节 = **2.98 MB**。
暴力余弦相似度 = 485 × 1536 ≈ 75 万次乘加，**实测 <5ms**。

**结论**：**不需要任何向量数据库**。FAISS / HNSW / sqlite-vec 全都用不上（还要加原生扩展）。
一张普通表 + 一层 for 循环足够，直到摘要数上万再说。

## 三、三个来源的取舍

| | 本地 ONNX（bge-small-zh） | 远程 API | 免依赖哈希向量 |
|---|---|---|---|
| 真语义 | ✅ | ✅ | ❌ 只是加权字面 |
| 依赖 | onnxruntime ~50 MB + 模型 25 MB | 无 | **无** |
| 延迟 | ~10ms/句 | **300~800ms/次** | <1ms |
| 成本 | 0 | 建库约 ¥0.05，查询可忽略 | 0 |
| 隐私 | 全本地 | **对话内容发给第三方** | 全本地 |
| 离线 | ✅ | ❌ | ✅ |

**远程 API 对本插件是致命的**：`agent/inbox/claimed` 是同步钩子，每轮聊天都要算一次
query embedding 才能重排——为了"联想更准"而给每条消息加 300~800ms，不划算。

所以真正的选项只有两个：**本地 ONNX**，或者**不做真语义**。

## 四、如果要做，架构长这样

```
用户消息
   ↓
① 词法召回（现有 gate）→ top 20      ← 不动，保证召回率和稳定性
   ↓
② 向量重排：算 query 与这 20 条的余弦  ← 新增
   ↓
③ 取 top 3 注入
```

**为什么必须这样分层**：

- **词法兜底**：embedding 服务挂了 / 模型没装 / 超时 → 跳过②，退化成现在的行为，
  **不会比现在更差**
- **成本可控**：只给 20 条候选算相似度，不给全库算
- **能解决真实问题**：`运维里的所有选项都有弹窗确认吗` vs `记忆库首次导入已完成`——
  字面共享"所有/确认"所以词法给高分，语义上毫无关系，向量距离远 → 重排后压下去

### 表结构

```sql
CREATE TABLE summary_vectors (
  summary_id  INTEGER PRIMARY KEY,
  model       TEXT NOT NULL,     -- 换模型必须全量重算，靠这列识别
  dim         INTEGER NOT NULL,
  vec         BLOB NOT NULL,     -- Float32Array 的裸 buffer
  norm        REAL NOT NULL,     -- 预存模长，省一次 sqrt
  updated_at  INTEGER NOT NULL
);
CREATE INDEX idx_sv_model ON summary_vectors(model);
```

`vec` 必须存 BLOB，**别存 JSON**——体积膨胀约 8 倍，解析也慢。

```js
function cosine(a, b, aNorm, bNorm) {
  let dot = 0;
  for (let i = 0; i < a.length; i++) dot += a[i] * b[i];
  return dot / (aNorm * bNorm || 1);
}
```

## 五、三个必须提前想好的坑

### ① 换模型要全量重算

不同模型的向量空间不可比。`model` 列就是用来识别的：检测到 `cfg.embedModel`
和表里的值不一致 → 全部标记待重算，后台慢慢补。不能混用。

### ② 增量更新必须异步 + 限流

挂在 `insertSummary` 之后异步排队。注意**扫描历史会话时会一次性灌进几百条摘要**，
必须限流（比如一轮最多算 50 条，剩下的下轮补），否则会把扫描拖成几分钟。

### ③ 查询 embedding 要缓存

同一句话反复算没意义。小 LRU（32 条）够用。

## 六、怎么验证有没有变好

`recall_log` 里存着历史 query 和当时的命中，是现成的测试集：

1. 取最近 100 条 query
2. 分别跑「只词法」和「词法 + 向量重排」
3. 用同一标准打标：命中的摘要和 query 是否真的在聊同一件事
4. 对比准确率

**不跑这个对比就不该上**——很可能加了 50 MB 依赖，准确率只涨几个点。

0.4.18 的 hub 降权就是这么验的：12 条 query，hub 摘要出现次数 3 → 1。

## 七、如果以后要做，建议的推进顺序

1. **P0｜先跑通骨架，不接模型**
   建表、余弦计算、重排接入 `gate`、A/B 对比脚本。
   embedding 来源先接确定性哈希向量（n-gram 哈希到 512 维 + TF-IDF 加权）——
   它不是语义向量，但能验证整条管线、能测延迟、能跑 A/B。

2. **P1｜看 P0 的数据再决定**
   如果 P0 已经把假阳性压下去大半，就不必上模型；如果还差得远，再考虑本地 ONNX。
   onnxruntime 放 `optionalDependencies` + `dynamic import()`，装不上就降级。

3. **远程 API 只用于非实时路径**
   `memory_recall` 工具这类可以接受 300ms 的地方，别挂在自动联想上。
